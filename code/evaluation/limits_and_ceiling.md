# Limits and ceiling - what is fixable, what is provably not, and how close we are

Generated by `python3 code/evaluation/ceiling_analysis.py` from the final run (no hidden answers are used; every number below is reproducible).

## Summary

* Status (`deletion_status`) is decided from evidence, not from missing ids: 100% on all 32 public samples. The 10 NOT_APPLICABLE requests are certain (text classifier and the 10 privacy-intake events agree).
* Steps: our output has **3264** steps over 508 deletion requests. A data-only solver cannot produce about **94** golden steps (86 retained-audit-record ids and 8 account ids that no file contains) and should get about **9** step picks wrong by chance (18 tied requests).
* **Estimated achievable ceiling for a data-only solver: step precision ~ 99.7%, recall ~ 96.9%, F1 ~ 98.3%**, with status accuracy near 100%. Our public-sample step F1 is 99.2% (all 32) / 99.4% (case_11-32).

## 2. Provably impossible (information is not in the data)

### 2.1 Retained audit-record ids: 86 of 508 deletion requests

The golden samples (`case_18`, `case_20`) list a `VERIFY_RECORD_PRESENT` step for the person's retained audit record, yet the id is in no participant-visible file. The same pattern affects the evaluation set. Evidence that no solver can recover them:

1. Every `audit_record_*` id in any evidence file is tied to a person by an identifier (`subject_reference` / `lookup_key`). **Unlinked audit ids in the evidence: 0** (the only audit ids without a person are rows of a screenshot of a different person). There is no candidate to pick.
2. The activity stream has 196 `RETAIN_RECORD` (security archival) events; **0 of their ids appear in any evidence file** and none is tied to any request. They are noise, not the missing ids.
3. The id is not a function of the person: md5/sha1/sha256/crc32 of user id, id number, e-mail, name and e-mail hash, taken modulo 9000-10001, reproduce the true id in 4 of 29705 attempts over all 457 known pairs, which is the chance level (about 1 in 10,000).
4. Where the missing requests come from (primary evidence format): `customer_data_inventory.sql` x35, `service_resource_export.json` x29, `resource_lookup_trace.log` x18, `account_history_report.pdf` x1, `customer_export_console.png` x1, `object_storage_browser.png` x1, `marketing_profile_console.png` x1.
5. The collectors that print their own counters report no drops where audit ids are missing, i.e. the evidence is complete *as collected*: `resource_lookup_trace_20260310_061801.log`: dropped=0, queries=1; `resource_lookup_trace_20260529_074313.log`: dropped=0, queries=23; `resource_lookup_trace_20260713_093359.log`: dropped=0, queries=26; `resource_lookup_trace_20260926_103856.log`: dropped=0, queries=28. The id was simply never queried.
6. In the public samples the same gap appears in `case_18`, `case_20` and the golden answer still contains the step.

We therefore **omit** these steps (inventing an id could only add a false step). Expected loss: one verification step in about 17% of requests.

### 2.2 Account ids with no identifier and no peers: 8 request(s)

Requests without any account step: `case_33`, `case_45`, `case_52`, `case_53`, `case_60`, `case_61`, `case_63`, `case_412`. These are screenshot/PDF stories (or multi-request subjects) whose account never appears with an identifier and whose worker events lie outside the request's window; the activity stream offers several unclaimed accounts but no peer event with a usable clock to choose between them.

### 2.3 Legacy sample `case_04`

Expected `account_004` has no worker event, no identifier and no file listing it; the only regularity is that legacy ids equal the case number (`account_001`...`account_010`), which would be a case-family shortcut that does not generalise to the 518 and is deliberately **not** used.

### 2.4 Residual ties

After the clock, **18** requests still tie ({2: 18} by group size). They have *no* timed peer (account + retained audit record only, nothing else with a worker event), so every candidate is equally consistent. Expected wrong picks: about 9. They are flagged `ambiguous` in `audit_trail.jsonl`.

## 4. Ceiling estimate - method

Let S = 3264 predicted steps. A data-only solver (no oracle) cannot emit the 94 steps in 2.1/2.2 and gets, by chance, about 9 of the tied picks wrong (each wrong pick is one false and one missing step). Hence precision <= (S - 9) / S = 99.7% and recall <= (S - 9) / (S + 94) = 96.9% (F1 98.3%). Status accuracy is not limited by these gaps: a request is INCOMPLETE only through records that *are* visible (every violating record carries an identifier), and 153 requests are COMPLETE.

Caveats: the ceiling assumes the golden answers contain a step for every resource family the generator created (as in all 22 representative samples); evidence-id and ordering are deterministic functions of the other fields.
