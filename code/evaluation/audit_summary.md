## Recreation risks (what makes 'deleted' not stay deleted)

* 113 requests still have an enabled connector that can copy or recreate the subject's data; remediation always disables the flow **before** deleting downstream copies.
* 26 requests have a backup archive with restore access still open; remediation blocks the restore (the archive itself is retained per policy).

## How much of this is certain?

* Identity resolution used current and historical e-mails, hashes and phones for every request; no request was left unresolved.
* 18 of 508 deletion audits contain a resource id that is a coin-flip among same-day candidates (no identifier, no usable event clock). Those are flagged `ambiguous` in `audit_trail.jsonl`; a privacy officer should confirm them before sign-off. All other identifier-free ids are unique or clock-matched.
* Every finding cites the evidence file that proves it; evidence captured after `audit_at` is never cited.

## Reading the per-case trail

`audit_trail.jsonl` (repo root, regenerated by the command above) has one JSON object per request: resolved subject, evidence file, every resource with its state at audit time, the policy rule applied (`rule_xx`), whether it is a violation, which evidence proves it and how the resource was linked to the person.
